# llm-chat 产品需求设计文档

- 日期：2026-10-27
- 状态：已评审（builder check 通过），待用户最终确认
- 原始想法：见 `docs/功能需求.md`（保留原件不动）

## 1. 意图与背景（Why）

开发者本人想要一个**日常随身助理**：对话是唯一入口，随手把花销"丢"进去，随口问账、看新闻。它不是又一个记账 App 或新闻 App——所有功能都通过自然语言对话完成，而回答不只是一段文字：AGENT 根据问题实时生成**富交互界面**（账单卡片、统计图表、新闻列表），在聊天流内原生渲染。

技术上的核心尝试是 **Generative UI（json-render）+ SKILLS 化的 AGENT 架构**：功能全部封装为带详细工作流的 skill，后端能力封装为 API 供 AGENT 调用，界面组件注册为目录供 AGENT 选择。这套骨架未来可以持续挂新 skill。

**成功画面**：每天早上打开它说"今天有什么 AI 大新闻"，中午说"午饭花了 35"，月底问"这个月衣服花了多少"，每一步都得到贴切的卡片/图表回答。

## 2. 目标 / 非目标 / 反目标

### 目标（v1 全部交付）
1. 对话主界面：**单一聊天框**（无多会话，所有对话在一个流中）、流式输出、聊天记录入库、向上无限滚动 + 虚拟滚动加载历史、**前端内存中最多同时加载 100 条消息**
2. 记账 skill：自然语言记一笔（支出/收入）、**两级类目**（父类汇总查询 + 子类单独查询，如"交通成本"与"打车费用"）、多维度查询、修改、删除；**记账成功后视情况回一句俏皮话**（吐槽/夸奖/鼓励，引导开源节流，增加趣味性）
3. 新闻 skill：关键词搜索（自动联想扩展）、按热度浏览、固定权威来源（国内+国际）；**按需抓取，不问不查，无定时任务**；外文新闻：中文译题 + 正文≤100字中文摘要 + 原文链接
4. Generative UI：json-render 目录 + Vue 3 组件注册，AGENT 输出 spec 在消息内渲染；历史消息的富界面刷新页面后原样重现
5. SKILLS 架构：skill = 系统提示词中的详细工作流 + 注册的 tools；未匹配 skill 时返回友好的"暂不支持"提示；新增 skill 不动核心框架
6. **全局规则：所有数据增删改必须经过用户二次确认后才执行**

### 非目标（v1 明确不做）
- 多用户、登录、权限体系（单用户个人工具）
- 多币种、预算管理、报销标记、账单导出
- 新闻正文全文翻译（仅做≤100字中文摘要）、新闻评论
- 移动端 App（桌面浏览器优先，宽度自适应即可）
- 新闻源的用户界面配置（来源写死在代码/配置文件中）

### 反目标（即使技术上可行也不允许）
- AGENT 未经确认静默写库——**这是失败**，确认步骤不可绕过
- AI 输出绕过 catalog 约束直接生成代码/任意组件（json-render 的目录校验是安全护栏，不得绕过）
- 幻觉组件名、幻觉账单数据（组件必须在目录内；数据必须来自 API 返回，不得编造）

## 3. 核心用例

| # | 用户说 | 系统行为 |
|---|--------|---------|
| U1 | 今天买衣服花了200 | 提取{金额200,事项:衣服,类目:服饰,日期:今天,类型:支出} → 渲染确认卡片 → 用户点「确认」→ 入库 → 卡片变"已保存"+俏皮话（如"这周第3件衣服，衣柜在报警了👕"） |
| U1b | 退款到账50 | 类型:收入/退款 → 确认入库 → 夸奖式俏皮话（如"会省钱的人运气不会差💰"） |
| U2 | 什么时候买的衣服？ | 查询账单 → BillList 卡片列出每笔（日期、金额、事项） |
| U3 | 这个月花了多少钱？ | 汇总统计 → Metric 卡片（¥2,340）+ 可附按类目占比图表 |
| U4 | 上周交通成本多少？ | 时间+类目交叉查询 → Metric + 明细列表 |
| U5 | 昨天那笔衣服改成150 | 定位账单 → 确认卡片展示 变更前→变更后 → 确认后 PATCH → "已更新" |
| U6 | 把那件衣服的账删了 | 定位账单（多笔匹配则先列表让用户指认）→ 删除确认卡片 → 确认后删除 |
| U7 | 帮我查今天关于AI的新闻 | 关键词扩展(AI→人工智能/LLM/大模型...) → 按需抓取+检索 → NewsList 卡片（中文译题+≤100字摘要+原题+来源+热度+时间+链接） |
| U8 | 今天有什么热点新闻？ | 热度模式 → 各来源按热度分排序 → NewsList |
| U9 | 你好，你能干什么？ | "暂不支持"话术兼作能力自介绍："目前支持：📝记账…📰新闻…"（v1 不做普通闲聊） |
| U10 | 帮我订机票 | "暂不支持该功能，目前支持：📝记账（记录/查询/修改/删除）、📰新闻（关键词搜索/热点浏览）" |
| U11 | "记一笔午饭" → 追问"花了多少钱？" → 用户只回"35" | 碎片补充与上一轮追问合并为完整账单（多轮上下文）→ 出确认卡片 |
| U12 | 午饭账单待确认时先去查了新闻，随后说"把刚才那笔午饭确认一下" | 提议未失效（TTL 内）→ 重新展示原 op_id 卡片 → 确认入库，旧流程完成 |

补充规则：
- **适用于所有 skill**：匹配到 skill 但关键信息缺失（如记账没说金额、查新闻没给主题）→ 纯文字追问，不出卡片、不调用 API
- 日期解析以服务器时区 Asia/Shanghai 为准，支持 今天/昨天/前天/上周X/本月X号/10月1日 等表达
- 金额支持 元/块/万元 表达，统一为人民币，内部以"分"为整数存储

## 4. 总体架构

```
┌─────────────────────────────┐
│  前端 Vue3 + TS             │
│  单一聊天界面（无会话列表）   │
│  json-render catalog+registry│
│  确认卡片交互、虚拟滚动       │
└──────────┬──────────────────┘
           │ HTTP / SSE
┌──────────┴──────────────────┐
│  后端 Node + TS（单服务）     │
│  ┌────────────┐ ┌─────────┐ │
│  │ API 层      │ │ Agent   │ │
│  │ 账单CRUD/统计│ │ 运行时   │ │
│  │ 新闻检索     │ │ skill路由│ │
│  │ 消息        │ │ tool调用 │ │
│  │ 动作执行     │ │ spec生成 │ │
│  └────────────┘ └─────────┘ │
│  新闻按需抓取(无定时任务)     │
└──────────┬──────────────────┘
           │
┌──────────┴─────┐ ┌─────────┐
│ SQLite 单文件DB │ │ 智谱API  │
│ (better-sqlite3)│ │glm-5.3- │
│                │ │  flash  │
└────────────────┘ └─────────┘
```

要点：
- 后端是**一个服务**，内部分 API 层与 Agent 运行时；Agent 通过内部函数调用 API 层（同进程，不出网络）
- 大模型走智谱开放平台兼容接口（glm-5.3-flash，需 function calling；具体兼容端点形式在实现期验证）
- SSE 流式推送 AI 回复（文字与 json-render spec 按行分离，inline 模式）

## 6. 数据模型（SQLite）

**messages** — 消息（单一聊天流，无会话表）
- id, role(user/assistant), content_text, spec_json(NULLABLE，编译后的 json-render spec，历史富界面重现用), created_at
- 索引：(created_at)

**bills** — 账单
- id, type('expense'/'income'), amount_cents(INTEGER), item(事项原文), category_id(叶子类目ID，见 categories), date('YYYY-MM-DD'), note, source_message_id(可空，溯源哪句话记的), created_at, updated_at
- 索引：(date), (category_id), (type)

**categories** — 两级类目（种子数据，固定清单；父类汇总、叶子记账）
- id, name, parent_id(NULLABLE，指向父类), kind('expense'/'income')
- bills.category_id 必须指向**叶子类目**（无子类的节点）；父类查询时经 parent_id 展开为全部子类汇总
- 种子清单（父 → 叶子）：
  - 餐饮：三餐、饮料奶茶、零食、聚餐
  - 服饰：衣服、鞋帽、饰品
  - 交通：加油、打车、停车、公交地铁、火车机票
  - 居住：房租水电、物业、家居
  - 娱乐：电影演出、游戏、旅行
  - 医疗：药品、门诊
  - 教育：书籍、课程
  - 日用品：清洁洗护、纸品、其他日用
  - 数码：设备、配件、软件订阅
  - 人情往来：礼物、随礼红包
  - 其他支出（无子类）
  - 收入（单级）：工资、退款、红包、其他收入
- LLM 记账时选叶子：说法明确（"加油300"→交通/加油）选具体叶子；只能定到父类（"花点钱吃饭"→餐饮/三餐）选最合理叶子；实在不行落"其他支出/其他收入"

**news_items** — 新闻缓存
- id, source(枚举), external_id(来源内唯一，去重), title(原题), title_zh(中文译题，可空——外文条目展示时惰性生成并缓存), summary_zh(正文≤100字中文摘要，可空，同上；生成失败降级为RSS简介或省略), url, published_at, heat_score(0-100 归一化), fetched_at
- UNIQUE(source, external_id)
- FTS5 虚表覆盖 title、title_zh

**news_fetch_runs** — 抓取运行记录（按需触发，每次查询期抓取记一行，观测各来源健康度）
- id, source, status('ok'/'error'), item_count, error, started_at, finished_at

**op_proposals** — 写操作提议全生命周期（二次确认的服务端载体 + 幂等 + 历史还原数据源）
- op_id PRIMARY KEY(**服务端生成** UUID，防模型幻觉撞号), kind('bill_create'/'bill_update'/'bill_delete'), payload_json, status('pending'/'executed'/'cancelled'/'expired'), result_json(执行结果，幂等重放用), created_at, executed_at（单一聊天流：全局同时最多 1 个 pending）
- 用途：①确认按钮防双击/重放（重复提交直接返回首次结果）②服务端强制提议失效 ③历史消息中确认卡片按最终状态只读还原

## 7. 后端 API 设计（REST，前缀 /api）

**聊天**
- POST /chat  body: {content} → SSE 流（文字部分 + spec JSONL 部分 + 结束标记）
- GET /messages?before_id=&limit= 向上分页（无限滚动）

**账单**
- POST /bills  {type, amount_cents, item, category, date, note?, op_id} → 幂等创建
- PATCH /bills/:id {变更字段, op_id}
- DELETE /bills/:id {op_id}
- GET /bills?from=&to=&category=&type=&q=&limit=&offset&order=date_desc → 列表
- GET /bills/stats?from=&to=&type=&group_by=(category|date)&metric=sum → 聚合统计

**新闻**
- GET /news/search?q=关键词(可多个逗号分隔)&mode=(keyword|hot)&source=&limit= → 无定时任务：命中缓存且未过期(来源级 TTL 30min)直接返回；否则**同步并行抓取**涉及来源（单来源超时 8s，超时/失败回退现有缓存并在结果中注明数据时间）
- GET /news/sources → 各来源状态与最近抓取时间
（不问不查：无任何查询发生时，进程不产生新闻外网请求）

**动作（json-render 确认按钮）**
- POST /actions/:name  body: 该 action 在 catalog 中声明的 params（含 op_id）→ 服务端校验提议状态（见 8.3）→ 分发到对应业务操作 → 写库成功后生成俏皮话（见 8.4 第 8 步）→ 返回执行结果+俏皮话（卡片据此切换状态并展示）
- GET /ops?op_ids=a,b,c → 批量查询提议状态（历史消息渲染确认卡片时还原最终状态用）

错误约定：统一 JSON 错误体 {code, message}；AGENT 层捕获后转成友好文案 + ErrorState 卡片。

## 8. AGENT 运行时与 SKILLS

### 8.1 运行时机制
1. 系统提示词 = 基础人设（中文助手，简洁）+ 各 skill 的路由描述与详细工作流 + `catalog.prompt({ mode: "inline" })` 生成的组件/动作说明
2. **上下文组装（每次 /chat 调用）**：
   - **服务端状态注入**：当前 pending 提议（op_id、kind、payload 摘要）注入系统提示词尾部——模型始终知道"有哪笔账待确认/待补充"，不依赖从历史卡片 JSON 自行还原
   - **聊天历史**：最近 20 条消息（token 超预算时从更早处截断）；assistant 消息的 spec 不回传完整 JSONL，压缩为一行摘要（如 `[卡片: BillConfirmCard 衣服 ¥200 op_xxx]`）
3. **意图路由含"进行中流程"优先**：若输入是对上一轮追问的补充（如只回"200"）、或针对 pending 提议的确认/恢复/取消，优先归入进行中的 skill 流程，再考虑新意图
4. 注册 tools（见各 skill），调用 glm-5.3-flash；循环处理 tool_calls 直到产出最终回复
5. 回复格式遵循 json-render inline 模式：先对话文字，后逐行 JSONL patch；无需 UI 时纯文字
6. 全程 SSE 流式吐给前端；最终文字+spec 持久化到 messages
7. 工具入参用 zod 校验，模型重试最多 2 次，仍失败走异常话术

### 8.2 路由规则（写在系统提示词中，模型执行）
- 命中记账意图 → 记账 skill（细分为记录/查询/修改/删除四个子流程）
- 命中新闻意图 → 新闻 skill
- 其他（含问候、闲聊、问能力边界）→ "暂不支持该功能，目前支持：📝记账（记录/查询/修改/删除）、📰新闻（关键词搜索/热点浏览）"——该话术兼作能力自介绍；**v1 不做普通对话路由**

### 8.3 全局规则：写操作二次确认（服务端强制，不可绕过）
- AGENT **没有**可直接写库的 tool。写操作分两阶段，提议生命周期由服务端 op_proposals 表承载：
  - **提议阶段**：AGENT 提取数据 → 调 `propose_op(kind, payload)` tool → **服务端生成 op_id** 并落库为 pending → AGENT 用返回的 op_id 生成确认卡片 spec（BillConfirmCard，含数据载荷 + 确认/取消动作），此阶段零写库
  - **执行阶段（按钮通道）**：用户点「确认」→ 前端直接调 POST /actions/*（不经过 LLM）→ 服务端校验提议仍有效 → 写库 → 状态置 executed、记录 result_json → 卡片切"已成功"；点「取消」→ cancel_op → 卡片变"已取消"
- **服务端强制失效**（前端置灰仅是体验层）：仅三种情况失效——① 超过 10 分钟未处理；② 用户明确取消；③ 出现**新的写提议**（自动取代，全局同时最多 1 个 pending）。失效后点确认返回"提议已过期，请重新发起"
- **话题切换不作废提议，流程可恢复**：确认中途切去查新闻等其它话题，旧提议保持 pending（TTL 内）；用户可点旧卡片「确认」，或说"把刚才那笔午饭确认一下"——AGENT 从注入的 pending 状态识别意图，重新展示同 op_id 确认卡片或直接 execute_op 完成原记账。单一聊天流中"流程"与"话题"解耦，切换话题不终结任何进行中的流程
- **文字确认通道**：用户回复"确认/对/保存吧" → AGENT 依据上下文调用受控执行 tool（execute_op，复用**卡片提议的同一个 op_id**）→ 同一套校验与幂等；两通道谁先执行谁生效，后到者收到"已执行"结果，杜绝双写
- 幂等：op_id 状态机保证重复提交（双击/重放/双通道）只产生一次写，重复请求返回首次 result_json

### 8.4 Skill：记账——记录（工作流逐步）
1. 从输入识别记账意图与类型（支出/收入）
2. 提取字段：金额（元/块/万归一为分）、事项、类目（映射到固定清单，映射不了→"其他支出/其他收入"）、日期（相对表达按服务器当日换算）、备注
3. 金额缺失或含糊（"花了好几百"？→ 追问具体金额）→ 纯文字追问，不出卡片
4. 疑似重复（同金额+同类目+同日期已存在）→ 卡片中附黄色提醒"今天已有一笔类似记录"，仍允许确认
5. 调 propose_op 取得 op_id，输出：简短说明文字 + BillConfirmCard spec（数据 + op_id + 确认/取消动作）
6. 用户点确认 → /actions/bill_create → 成功：卡片状态"已保存"+俏皮话（见第 8 步）；失败：卡片 ErrorState + 「重试」按钮
7. 异常：类目清单加载失败 → 归"其他"并文字提示；金额解析失败 → 追问
8. **俏皮话（写库成功后触发，按钮/文字两通道行为一致）**：服务端组装事实数据——新账单 + 本月同类目总金额与笔数 + 本月总支出 → 调 glm-5.3-flash 生成**一句**俏皮话（≤30字）：
   - 语气规则（视情况选一）：同类目金额偏高或频次偏高 → 朋友式吐槽（吃饭太贵、购物太频繁…）；收入/退款类 → 夸奖；金额异常大 → 温和提醒；普通小额记录 → 一句简短鼓励或不说话
   - 红线：吐槽必须基于传入的真实统计，不得编造数据；不连环说教、不冒犯；生成失败或超时(5s) → 静默省略，绝不影响记账主流程
   - 展示：按钮通道——俏皮话随 /actions 结果返回并存入 result_json，卡片 saved 状态底部气泡展示（历史重现经 GET /ops 原样恢复）；文字确认通道——AGENT 调 execute_op 取回俏皮话写进最终回复文字

### 8.5 Skill：记账——查询/统计
1. 解析维度：时间范围（今天/昨天/本周/本月/今年/自定义区间）、类目、类型、关键词、粒度（明细列表/总额/按日汇总/按类目汇总）
   - **类目解析支持两级**：说"交通/交通成本"→父类汇总（含加油+打车+停车+…全部子类）；说"打车/加油/停车"→子类单独查询；同义词归一（"打的/出租车"→打车）
   - 用户说法不匹配任何类目（如"沐浴露花了多少"）→ 用事项关键词(q)兜底检索
2. 调 GET /bills 或 /bills/stats（总额类问题必须走 stats 接口，禁止让模型心算列表求和；category 传父类名时服务端自动展开为其全部子类）
3. 空结果 → 文字"X月还没有记账记录哦"（可附 EmptyState 卡）
4. 明细 → BillList（超 20 条卡片内部分页/折叠）；总额 → Metric + StatChart（按类目 bar / 按日 line）
5. 定位类问题（"什么时候买的衣服"）→ BillList 按时间倒序，突出日期
6. 异常：API 失败 → 文字致歉 + 建议重试

### 8.6 Skill：记账——修改/删除
1. 依用户描述调 GET /bills 定位目标（时间+事项+金额线索）
2. 0 笔 → 文字"没找到这笔记账"；多笔 → BillList 让用户指认（"第几笔"或补充特征）
3. 单笔 → 生成 BillConfirmCard：修改展示 变更前→变更后 diff；删除展示将删除的记录；动作分别为 bill_update / bill_delete
4. 确认执行、状态反馈、幂等保护同 8.3/8.4
5. 异常：目标记录刚被删除 → 文字说明当前状态

### 8.7 Skill：新闻查询
1. 识别模式：关键词搜索 / 热点浏览 / 指定来源浏览；完全没有主题/关键词且未明确要热点榜 → 纯文字追问（"想了解哪方面的新闻？也可以直接说'看热点'"），不出卡片
2. 关键词扩展：模型在调用前就地扩展（AI→AI、人工智能、LLM、大模型…），扩展词与原词一并传给检索工具
3. 调 GET /news/search（keyword 模式多词 OR 检索；hot 模式按 heat_score 排序，可带 source 过滤）
4. 展示前补全外文条目的译题与摘要（缓存优先，惰性生成）：title_zh / summary_zh 为空 → 抓正文（readability 抽取；HN 取其链接指向的文章）→ 批量调 glm-5.3-flash 生成中文译题 + ≤100字中文摘要 → 回写 news_items 缓存；正文抽取失败降级用 RSS 自带简介，再失败该条只显原题
5. 渲染 NewsList：中文译题为主、≤100字中文摘要、来源徽标、热度、相对时间、原题+原文链接（外链跳转）
6. 结果为空 → 文字建议换关键词/看热点榜；来源抓取异常 → 文字说明"X来源暂时不可用"并展示其余来源；单条摘要失败不阻塞整列表
7. 时效与历史区间：默认查"今天"，可指定日期区间——HN/Guardian 按日期现抓历史区间，RSS 来源仅支持近期（约3~7天）；超出支持范围的来源跳过并在回答中**注明各来源支持的历史区间**，全部不支持则直接回复"不支持该时间范围的查询"；首次按需抓取可能稍慢（并行+超时兜底），卡片注明数据时间

### 8.8 新增 skill 的扩展方式（写给出后续维护者）
新功能 = ①后端 API → ②catalog 增加组件/动作 → ③系统提示词追加工作流描述 + 注册 tools → ④前端 registry 挂组件实现。四步清单写进 README。

## 9. 前端设计

### 9.1 布局
- 单栏布局（无侧边栏）：顶部应用标题栏 + 消息流 + 底部输入框（Enter 发送/Shift+Enter 换行，发送中禁用并显示停止按钮 v1 可后置）

### 9.2 消息流与滚动
- 虚拟滚动：消息列表用虚拟列表组件（实现者选型：@vueuse/core useVirtualList 或 vue-virtual-scroller），DOM 只挂载可见区域
- **内存窗口上限 100 条**：初始加载最新 100 条；向上触顶拉取更早一页（20 条/页）并从另一端滑出等量消息，内存中始终 ≤100 条；滑出的消息再滚回来时按需重新拉取
- prepend 保持视口不跳动；流式期间自动追底；用户上翻时暂停追底，出现"回到底部"悬浮按钮

### 9.3 流式与渲染
> **2026-10-28 更新**：组件目录/Actions/Registry 的代码位置已随 features 重构迁移（catalog 定义在 `features/<名>/server/`、组件实现在 `features/<名>/web/`、契约单源在 `features/<名>/shared.ts`），本节清单内容不变；架构见 `2026-10-28-features-architecture.md`。
- SSE 消费：按 inline 模式分离文字与 JSONL patch，逐行编译 spec，Renderer 渐进渲染
- 组件目录（catalog，v1 清单，props 用 zod 定义并附 description 供 AI 理解）：
  - `BillConfirmCard`（提议数据、状态：pending/saved/cancelled/error、变更前后 diff、确认/取消/重试动作、saved 态底部俏皮话气泡）
  - `BillList` / `BillItem`（日期、事项、类目、金额正负色）
  - `Metric`（label、value、format=currency/number）
  - `StatChart`（chart=bar|line，数据序列，标题）—— ECharts 封装
  - `NewsList` / `NewsItem`（中文译题、≤100字中文摘要、原题、来源、热度、时间、原文链接）
  - `EmptyState`、`ErrorState`
- Actions 目录：`bill_create` / `bill_update` / `bill_delete` / `cancel_op` / `retry_op`（params 含 op_id 与数据载荷）
- Registry：catalog 类型 → Vue 组件映射；历史消息直接用库中 spec_json 渲染，不重新请求 LLM

### 9.4 历史重现
- messages.spec_json 存编译后 spec（消息不可变，不原地更新）；加载历史时文字与 UI 原样恢复
- 确认卡片渲染时按 op_id 调 GET /ops 批量取真实状态，按最终状态（executed/cancelled/expired/pending）只读展示——状态变化不回写消息，保持消息不可变假设

## 10. 新闻按需抓取管道（无定时任务，不问不查）

- 来源（7 家）：
  | 来源 | 地区 | 接入 | 热度 | 历史区间 |
  |---|---|---|---|---|
  | 新华社 | 国内 | RSS/RSSHub | 频道排序位置代理 | 仅近期（RSS 窗口） |
  | 人民日报 | 国内 | RSS/RSSHub | 同上 | 仅近期 |
  | 新浪网 | 国内 | RSS/RSSHub（尝试排行榜） | 有则用 | 仅近期 |
  | Hacker News | 国际 | Algolia 搜索 API（支持日期过滤） | points+comments | **支持历史** |
  | BBC News | 国际 | 官方 RSS | 无→时间合成 | 仅近期 |
  | The Guardian | 国际 | 开放 API（免费 key，支持日期过滤） | 基础热度字段 | **支持历史** |
  | TechCrunch | 国际 | RSS | 无→时间合成 | 仅近期 |
- 触发时机：**仅** GET /news/search 时——涉及来源缓存未过期(来源级 TTL 30min)直接用缓存；否则并行抓取涉及来源，单来源超时 8s，超时/失败回退现有缓存并在结果中注明数据时间
- **历史区间规则（降级已确认）**：默认可查"近期"（各 RSS 来源自然窗口，约 3~7 天，以实际可得为准）；用户查更早区间时——HN 与 Guardian 支持按日期过滤**现场抓取指定区间**（仍是问了才查）；仅近期来源跳过并在回答中注明"该来源不支持历史区间查询"；全部来源均不支持 → 直接返回不支持提示，并说明各来源支持的时间范围
- 抓取后：按 (source, external_id) 去重 upsert 入库
- 译题与摘要（惰性生成，缓存于 news_items.title_zh / summary_zh）：对**将展示**的外文条目批量调 glm-5.3-flash——中文译题 + 正文≤100字中文摘要；正文用 readability 抽取（HN 取链接指向文章），抽取失败降级为 RSS 简介，再失败则该条只显原题，不阻塞列表
- 国内新闻为中文，标题原样展示，不做摘要
- heat_score 各来源内归一化 0-100；无真实热度数据的按"是否首页/前排 + 新近度"合成
- 失败处理：单来源失败记 news_fetch_runs，不影响其他来源；/news/sources 暴露健康状态
- 风险：RSSHub 公共实例可用性不稳——实现期验证，必要时自托管 RSSHub 或降级跳过该来源并如实报告

## 11. 约束与风险

**访问约束（用户已定）**：仅本机部署访问（监听 127.0.0.1），无鉴权，不做公网/局域网暴露。

| 风险 | 影响 | 缓解 |
|---|---|---|
| glm-5.3-flash 工具调用稳定性 | 记账提取错乱 | 严格 zod 校验+重试2次；写操作有人工确认兜底 |
| 智谱兼容端点形式未验证 | Agent 层联调受阻 | 实现期先用最小脚本验证 tool calling 与流式，再定 SDK |
| @json-render/vue 对 inline 模式辅助函数的覆盖度 | 聊天内 spec 分离需手写 | JSONL 按行解析逻辑简单可手写；实现期查 vue skill 文档 |
| 国内源 RSS 可达性 | 新闻源缺数 | 自托管 RSSHub / 降级并在来源状态中如实展示 |
| FTS5 编译可用性 | 关键词检索降级 | better-sqlite3 默认含 FTS5，验证后不行降级 LIKE |
| 虚拟滚动 + prepend 不跳动 | 体验问题 | 选型时验证此场景，必要时加载期间锁滚动位置 |
| 按需抓取首查延迟 | 首次新闻查询慢几秒 | 并行抓取+8s超时+缓存兜底+文字进度提示 |
| 外文正文抽取质量 | 摘要无料可写 | readability 失败降级 RSS 简介，再失败只显原题不阻塞 |
| Windows 开发环境 | 脚本/路径兼容 | 统一 cross-env，路径用 node path API |
